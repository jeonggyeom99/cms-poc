# CMS AI PoC 발표 목차 — AI 담당 파트

## 발표 방향

- 범위: 저장소에 구현된 AI 종합 분석, 질의응답, 진단 보고서 생성.
- 권장 분량: 본문 12장, 약 10~15분. 발표 시간과 청중이 정해지지 않아 기술과 업무 활용을 함께 설명하는 구성으로 제안한다.
- 핵심 메시지: **서버가 계산한 진단 근거를 AI가 종합해 설명하고, 검증된 결과를 현장 점검과 보고 업무에 연결한다.**
- 전체 발표에서 데이터 수집·Trend/FFT 알고리즘을 다른 담당자가 설명한다면, AI 파트에서는 입력과 역할만 짧게 연결한다.

## PPT에 바로 넣을 목차

1. AI 도입 목적과 역할
2. 구현된 AI 기능과 사용자 흐름
3. AI 분석 아키텍처
4. 분석 근거 준비와 이력 압축
5. 설비 단위 종합 분석
6. 도구 호출 기반 질의응답
7. 응답 검증과 오류 대응
8. 응답 시간 개선과 캐시 전략
9. 진단 PPT·이메일 초안 생성
10. 실제 데이터 기반 검증 결과
11. 주요 기능 시연
12. 현재 한계와 다음 단계

## 기술 설명에 넣을 핵심 포인트

### 4장 — 근거를 준비하는 방법

- Trend: 최신 추세 측정일 기준 최근 90일, 월별 평균·표본 수·실제 관측 기간·이전 월 대비 변화량.
- FFT: 측정 모드·단위·측정점·RPM·주파수 범위·분해능별 그룹 분리.
- 각 그룹의 월별 주요 성분은 최초·최신·최소·최대 **실제 관측값**과 기록 ID·측정일을 보존한다. FFT의 월별 극값을 월평균으로 설명하지 않는다.
- 최초·최신·최초 이상·주요 진폭 최대 기록에서 중복을 제거해 그룹당 최대 6개 대표 기록을 선정한다.
- 관련 과거 이력과 해석하지 못한 기록의 제한도 제공한다. 원본 FFT 주파수·진폭 배열은 모델 입력에서 제외한다.

### 6장 — 종합 분석과 채팅의 도구 사용

| 구분 | 근거 조회 방식 | 발표에서 강조할 점 |
|---|---|---|
| 설비 종합 분석 | 첫 요청에 근거 제공. 필요할 때 `get_fft_evidence`, `get_fft_history_evidence`, `get_related_history` 추가 호출 | 충분한 근거가 있으면 AI 요청 한 번으로 완료. 추가 조회는 최대 2단계·4개 호출, FFT 이력 페이지는 최대 50개 |
| 채팅 | 질문에 따라 `get_trend`, `get_fft`, `get_bearing_fft`, `get_related_history` 선택 | 질문의 설비·기간·기록을 확인하고 도구 결과를 사실 근거로 사용 |

질문 예시: “이 설비의 8월 31일 FFT는 어떤 상태인가요?” 날짜를 지정하면 해당 날짜를 조회하며, 화면에서 선택된 다른 날짜 기록을 대신 사용하지 않도록 지시한다.

### 7장 — 신뢰성 확보

- 구조 검증: 정해진 JSON 필드와 값의 범위를 검사한다.
- 근거 검증: 응답의 측정 수치·단위·관측 기간·대표 기록·원인 주장을 전달한 근거와 대조한다.
- 해석 제한: 1X 우세만으로 축정렬 불량을 단정하지 않으며, 베어링 정보가 없으면 해당 진단의 제한을 표시한다.
- 보정: 같은 근거로 응답을 다시 생성하고, 보정 중에는 추가 도구를 호출하지 않는다.
- 운영 추적: 요청 ID와 실패 단계 등을 로그로 남긴다. API 키·원문 AI 응답·측정 배열은 로그에 기록하지 않는다.

### 9장 — 보고서 생성의 범위

- 발표용 전체 덱 자동 생성 기능과 구분해, 구현된 산출물은 **한 장짜리 설비 진단결과 PPTX**로 소개한다.
- PPT 검증은 LibreOffice·Poppler로 렌더링한 이미지와 도형·표 좌표를 함께 사용한다. 검증 상태는 통과·경고·미완료로 전달한다.
- 레이아웃 수정 시 수치·조건·불확실성·서로 다른 진단 근거를 보존한다. 문구 제거는 완전히 동일한 반복 문장에 한정한다.
- 이메일 기능은 본문과 그래프의 복사를 지원한다. 실제 메일 전송은 구현 범위에 포함되지 않는다.

## 10장에 사용할 검증 수치

출처: [초기 컨텍스트 기반 AI 분석 검증](validation/ai-prefetched-context.md). 아래는 **2026-10-06에 기록된 기존 실측**이며 이번 목차 작성에서 재측정하지 않았다. 당시 모델은 `gpt-5.6-luna`, 분석 기준은 `v9-prefetched`였다. 현재 코드의 분석 기준은 이후 변경되었으므로 현재 버전의 성능 보장으로 제시하지 않는다.

| 대상 | 측정 횟수 | 전체 시간 | AI 요청 수 | 추가 도구 호출 | 응답 보정 |
|---|---:|---|---|---|---|
| 설비 8 | 3회 | 13.047~17.156초, 중앙값 15.416초 | 모두 1회 | 모두 0회 | 모두 0회 |
| 설비 9 | 3회 | 12.276~22.956초, 중앙값 13.776초 | 1~2회 | 0~1회 | 0~1회 |
| 설비 1~5 | 설비당 1회 | 11.196~20.349초 | 모두 1회 | 모두 0회 | 모두 0회 |

- 설비 8·9의 6회 중 4회가 AI 요청 1회로 완료됐고, 5회는 추가 도구를 사용하지 않았다.
- 측정 시간에는 입력 준비·AI 요청·로컬 도구 처리·결과 검증이 포함된다. 서버 시작·HTTP·브라우저 렌더링·캐시 파일 저장 등은 제외된다.
- 첫 요청 입력은 설비 8·9에서 각각 42,388·14,709토큰이었다. 초기 입력량과 응답 지연의 추가 개선 여지가 있다.
- 이전 코드 측정과는 표본 수·응답·조회 계획·제공자 캐시 상태가 달라, 일정한 배수의 성능 개선으로 일반화하지 않는다.
- 검증 기록의 PASS는 해당 사례의 응답이 근거 검사 기준을 충족했다는 의미다. 실제 고장 진단 정확도나 전체 설비에 대한 통계적 정확도는 별도 평가가 필요하다.
