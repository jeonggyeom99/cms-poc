# CMS AI PoC 현재 동작 정리

> 이 문서는 2026-09-10 기준 현재 구현을 설명한다. 개선 논의를 위한 현황 자료이며, 진단 규칙의 타당성이나 현장 판정의 근거를 보증하지 않는다.

> 2026-09-18 통합 참고: 아래 내용은 9월 10일의 동작 기록이다. 이후 추가된 대시보드 AI 채팅은 공통 분석 서비스를 통해 추세·FFT·베어링 분석을 조회하며, 과거 날짜/기간 선택과 FFT 기록 변경 시 대화 유지 기능을 제공한다. 시간 파형은 유효한 샘플링 주파수가 있으면 초 단위 시간축을 사용한다. 최신 코드에는 연관 이력 API도 별도로 제공되므로, 아래 API 목록은 전체 목록이 아니다.

## 1. 프로그램 목적과 구성

CSV로 받은 설비 상태감시(CMS) 데이터를 조회하고, 추세·FFT·과거 진단 이력을 한 화면에서 확인하는 웹 PoC다. 선택한 FFT 기록을 기준으로 규칙 기반 1차 분석을 표시하고, 선택적으로 OpenAI API를 이용한 보조 분석, 진단 PPT, 이메일 초안을 만든다.

```text
data/*.csv + app/equipment_metadata.json + equipment-status-demo/*.js
                         │
                         ▼
              FastAPI 서버 (app/main.py)
              ├─ CSV 로드·정규화·규칙 기반 분석
              ├─ JSON API / AI API / 보고서 API
              └─ 정적 HTML·JavaScript 제공
                         │
                         ▼
       설비 현황 (/) ──→ 상세 대시보드 (/dashboard)
                         │
                         ├─ 과거 이력 (/history)
                         ├─ AI 종합 분석
                         ├─ 진단 PPTX 다운로드
                         └─ 이메일 본문 복사
```

실행 방법은 다음과 같다.

```bash
uv sync
uv run uvicorn app.main:app --reload
```

## 2. 입력 데이터와 서버 시작 시 처리

서버가 시작될 때 `data/` 폴더의 CSV를 한 번 읽어 메모리에 보관한다. 파일명 맨 앞의 숫자를 데이터셋 ID로 사용하고, 같은 ID의 파일을 하나의 설비 데이터셋으로 묶는다.

| 파일 종류 | 파일명 판별 | 필수 내용 | 사용처 |
| --- | --- | --- | --- |
| Trend | 파일명에 `Trend` | `DataDate`, `VelAve`, `AccAllAve` | 추세 그래프, 상태, Level 분석 |
| FFT | 파일명에 `FFT` | 측정일시·모드·주파수·라인 수·`ResultData` | FFT/시간파형 그래프, 주파수 분석 |
| WarningStatus | 파일명에 `WarningStatus` | 발생 시각, 속도 주의/위험 기준값 | 임계값 표시, Level 비교 |
| 과거 이력 | `CMS history.csv` | 진단일·설비·결함·조치 등 | 이력 화면, 연관 이력, AI 맥락 |

`app/equipment_metadata.json`에는 RPM, 베어링 제조사·형번 등의 보강 메타데이터가 있다. 베어링 결함계수는 `data/0. Bearing_Fault_Frequency_Master_File.txt`에서 읽는다. 메타데이터 또는 CSV 일부가 없거나 형식이 틀려도, 가능한 다른 데이터는 계속 제공하며 API 응답의 오류 정보에 기록한다.

FFT의 `ResultData`는 little-endian float32 바이트열로 해석한다. FFT 원본 배열은 상세 레코드를 요청할 때 읽어 그래프에 전달하며, AI 호출에는 보내지 않는다.

## 3. 화면별 사용자 흐름

### 설비 현황: `/`

1. 별도 JavaScript 데이터의 설비 분류 트리와 `/api/datasets`의 실제 데이터셋 요약을 결합한다.
2. 공장, 공정, 설비 종류, 상태, 설비명으로 목록을 필터링할 수 있다.
3. 실제 CMS 데이터가 연결된 센서는 클릭하면 `/dashboard?dataset=<ID>`로 이동한다.
4. 상태는 Trend의 상승 경향 결과를 주로 이용한다. 다만 현재 구현에는 `V056`, `V191` 두 설비를 무조건 `심각`으로 표시하는 예외가 있다.

### 상세 대시보드: `/dashboard`

1. `/api/datasets`에서 설비 선택 목록을 가져온다.
2. URL의 `dataset`이 유효하면 해당 설비를, 아니면 첫 번째 설비를 선택한다.
3. `/api/dashboard/{dataset_id}`에서 기본 데이터(기본 선택 FFT 레코드 포함)를 받아 다음을 그린다.
   - 속도·가속도 Trend 그래프: 1개월 / 3개월 / 전체 기간 전환 및 확대 가능
   - FFT 스펙트럼, 시간 파형 그래프: 확대 가능
   - 최근 3개월 기반 속도 기준값(Level) 분석
   - 조건을 만족하는 FFT 레코드 목록과 선택 레코드의 진단 결과
   - 같은 설비 또는 같은 결함 유형의 과거 진단 이력
4. FFT 목록에서 다른 기록을 선택하면 `/api/dashboard/{dataset_id}/fft/{record_id}`로 원본 배열을 포함한 해당 기록을 추가 요청한다. 브라우저 내 캐시를 사용하며, 선택이 바뀌면 AI 분석 및 보고서 결과를 초기화한다.

`until=YYYY-MM-DD` 쿼리 파라미터가 있으면 해당 날짜 23:59:59까지의 Trend, FFT, WarningStatus만 사용해 과거 시점 화면을 재구성한다. 과거 이력 화면의 `그래프 보기`가 이 방식으로 대시보드에 연결된다.

### 과거 진단 이력: `/history`

`/api/history`의 이력을 공정 및 키워드로 검색한다. 행을 펼치면 현상, 분석, 결과, 피드백과 측정 정보를 볼 수 있다. 연결된 데이터셋이 있는 이력은 진단일 기준의 대시보드로 이동할 수 있다.

## 4. 규칙 기반 분석 로직

### 설비 상태와 Trend 상승 경향

Trend의 `VelAve`가 최소 143개 있어야 상승 경향을 판단한다.

1. 매우 낮은 이상값을 보정한다.
2. 72개 시점 이동평균을 만든다.
3. 마지막 72개 이동평균에 선형회귀를 적용한다.
4. 기울기가 `1 / (24 × 14) mm/s/hour`보다 크면 `상승 경향(caution)`, 아니면 `정상(normal)`으로 표시한다.

데이터가 143개보다 적으면 `추세 판단 불가(unknown)`이다. 현재 설비 현황의 상태는 이 Trend 규칙을 기준으로 하므로, FFT 이상 자체가 전반 상태를 자동으로 악화시키지는 않는다.

### 속도 Level 분석

최근 3개 달력 월의 VelAve를 대상으로 IQR(사분위 범위) 밖의 값을 제외한다. 남은 값의 평균을 기준으로 권장 주의값은 평균의 2배, 권장 위험값은 평균의 4배로 계산한다. WarningStatus가 있으면 현재 설정값과 권장값의 차이도 보여 준다.

### FFT 공통 피크 추출과 목록 노출

양수 주파수에서 진폭 상위 후보를 고르고, 가까운 주파수를 피크 그룹으로 묶어 최대 5개 피크를 표시한다.

| 측정 모드 | 단위 | 피크 후보 기준 | 그룹화 범위 |
| --- | --- | ---: | ---: |
| 속도 (`3`) | mm/s | 0.5 이상 | 1 Hz |
| 가속도 ALL (`0`) | g | 0.2 이상 | 5 Hz |
| 가속도 ENV (`2`) | g | 0.2 이상 | 5 Hz |

FFT 분석 목록에는 최대 진폭이 0.5 초과이거나, 채취 종류가 주의경보(`3`)·위험경보(`4`)인 기록만 표시한다. 기본 선택은 이 목록의 비-ALL 기록을 우선하고, 없으면 속도 기록, 그마저 없으면 최신 기록이다.

### 속도 FFT: 회전계 결함 후보

RPM으로 축 회전 주파수 `1X = RPM / 60`을 구한다. `1X`, `2X`, `3X` 주변 ±1 Hz에서 최고 피크를 찾는다.

- 1X가 0.5 mm/s 미만이면 판정하지 않는다.
- `2X / 1X > 0.4` 또는 `3X / 1X > 0.3`이면 `Misalignment` 후보다.
- `2X / 1X < 0.2`이고 `3X / 1X < 0.1`이면 `Unbalance` 후보다.
- 나머지는 복합 또는 불확실로 표시한다.
- RPM이 없거나 유효하지 않으면 이 분석은 보류한다.

### 가속도 ALL/ENV FFT: 베어링 결함 후보

RPM과 베어링 마스터의 BPFO/BPFI/BSF/FTF 계수로 각 결함의 1X, 2X, 3X 목표 주파수를 계산한다. 각 목표 주파수와 축 회전수 사이드밴드 주변 ±5 Hz에서 피크를 찾는다.

- 1X·2X·3X 중 하나가 0.5 g 이상이면 해당 결함을 이상 후보로 판단한다.
- 여러 후보면 고조파·사이드밴드 점수, 최대 피크, BPFO/BPFI/BSF/FTF 순으로 대표 결함을 고른다.
- 이상 후보가 없으면 BPFO를 기본 선택으로 두고 ‘베어링 결함 Peak 없음’을 표시한다.
- RPM, 제조사, 형번, 유효 결함계수 중 하나가 없으면 결함 주파수 판정은 하지 않는다.

## 5. AI 분석과 보고서

`OPENAI_API_KEY`가 설정된 경우에만 사용할 수 있다. 기본 모델은 `gpt-4o-mini`, 기본 제한시간은 20초이며 `.env` 또는 운영 환경변수로 변경할 수 있다.

AI에 전달하는 것은 압축한 근거 데이터다.

- 설비 정보: 설비명, 측정 위치, RPM, 베어링, 현재 상태 등
- Trend: 기간, 표본 수, 통계, 30/90일 변화량, 임계값 상태, 상승 경향 결과
- 선택 FFT: 측정 조건, 상위 피크 최대 5개, 규칙 기반 진단·고조파·결함 요약, 최근 경보 FFT 최대 5개
- Level 분석과 데이터 품질 주의사항
- 선택 시점 이전의 동일 설비 또는 같은 결함 유형 과거 이력 최대 5건

원본 FFT 주파수/진폭 배열, API 키, 사용자의 브라우저 내 데이터는 AI로 보내지 않는다. 응답은 정해진 JSON 형식(위험 수준, Trend/FFT/이력 소견, 원인 후보와 신뢰도, 반증, 권장 조치)으로 검증한다. 같은 입력은 서버 메모리 캐시를 재사용하며 `다시 분석`은 캐시를 건너뛴다.

보고서 기능은 같은 AI 근거를 사용한다.

- `진단 보고서 저장`: 화면의 Trend/FFT 그래프 이미지와 AI 진단을 넣은 한 장짜리 PPTX 다운로드
- `이메일 본문 복사`: AI가 작성한 한국어 이메일 초안과 두 그래프를 서식 있는 클립보드 데이터로 준비. 실제 이메일 전송은 하지 않음

AI 분석은 기존 규칙 기반 판단의 보조 수단이며, 잔여수명·MTBF를 예측하지 않는다. 최종 판단은 운전 조건과 현장 점검을 포함해 담당자가 한다.

## 6. 주요 API

| API | 용도 |
| --- | --- |
| `GET /api/datasets` | 설비 선택/현황용 데이터셋 요약 |
| `GET /api/dashboard` | 첫 데이터셋의 상세 데이터 |
| `GET /api/dashboard/{dataset_id}?until=` | 선택 설비의 상세 데이터 |
| `GET /api/dashboard/{dataset_id}/fft/{record_id}?until=` | 선택 FFT의 원본 배열 포함 상세 기록 |
| `GET /api/history` | 과거 진단 이력 |
| `POST /api/dashboard/{dataset_id}/ai-analysis` | AI 보조 분석 |
| `POST /api/dashboard/{dataset_id}/diagnostic-ppt` | PPTX 생성 |
| `POST /api/dashboard/{dataset_id}/email-draft` | 이메일 초안 생성 |

## 7. 현재 구현의 경계와 개선 논의 출발점

다음은 결함이라기보다, 현재 PoC의 명시적인 범위 또는 개선 후보다.

1. 데이터는 서버 시작 시 한 번만 읽는다. CSV 변경을 반영하려면 서버 재시작이 필요하다.
2. 설비 현황의 일부 분류 데이터와 두 설비의 `심각` 상태는 JavaScript에 고정되어 있다. 실제 데이터·상태 규칙과 분리될 가능성이 있다.
3. 전체 설비 상태는 주로 Trend 상승 경향으로 결정된다. FFT 경보, Level 초과, AI 결과를 통합한 위험 점수는 없다.
4. Trend 상승 판단은 고정된 72시간 창, 143개 최소 표본, 단일 기울기 임계값을 사용한다. 설비별 운전 패턴·정지 구간·계절성은 반영하지 않는다.
5. FFT 진단은 RPM·베어링 계수·고정 허용오차와 임계값에 의존한다. 실제 회전수 변동, 부하, 측정 위치, 신호 품질, 기어/전기적 결함 등은 제한적으로만 다룬다.
6. AI 결과는 서버 메모리 캐시만 사용한다. 분석 이력, 사용자 피드백, 결과 승인, 감사 로그, 권한 관리는 없다.
7. 이력-데이터셋 연결은 현재 파일/메타데이터 기반이며, 명시적인 설비 마스터 ID 체계나 데이터 수집 파이프라인은 없다.
8. CSV 유효성 오류는 일부 데이터셋을 건너뛰고 로그/API 오류 정보로 남는다. 운영자용 데이터 품질 화면이나 알림은 없다.
9. 알림 발송·작업지시·외부 CMS/설비관리 시스템 연동은 구현되어 있지 않다.

## 8. ChatGPT와 논의할 질문 예시

- 현재의 Trend/FFT/Level 규칙을 하나의 설비 위험도와 우선순위로 결합하려면 어떤 지표와 검증 절차가 필요한가?
- 설비별 RPM 변동, 정지 구간, 부하 변화를 반영해 오탐을 줄이려면 입력 데이터와 알고리즘을 어떻게 바꿔야 하는가?
- 베어링 및 회전계 결함 진단 규칙에서 고정 임계값을 설비별 기준선으로 전환하는 실용적인 방법은 무엇인가?
- 현장 담당자가 AI 분석을 신뢰·검토할 수 있도록 근거, 불확실성, 승인 흐름을 UI와 데이터 모델에 어떻게 설계해야 하는가?
- CSV PoC를 실제 운영 시스템으로 전환할 때 데이터 수집, 저장소, 갱신, 권한, 감사, 알림을 어떤 단계로 도입해야 하는가?
