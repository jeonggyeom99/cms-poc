# 초기 컨텍스트 기반 AI 분석 검증

2026-10-06, 모델 `gpt-5.6-luna`, 개별 요청 제한 20초, 분석 기준 `cms-dashboard-analysis-v9-prefetched`로 검증했다. 기존 설비 8(V191)·9(V056) 데이터를 사용해 실제 OpenAI API를 호출했다. 사용자는 해당 데이터의 `api.openai.com` 전송과 실제 재측정을 승인했다.

## 측정 방법

대시보드 API와 동일한 입력 생성, 도구 executor, `OpenAIAnalysisGateway`, JSON·근거 검사와 보정 흐름을 사용했다. 임시 계측 스크립트가 각 SDK 요청과 도구 실행의 시간을 측정했다. 앱 결과 캐시는 우회했으며 기존 캐시 파일은 갱신하지 않았다. 제공자의 프롬프트 캐시는 기본 동작대로 유지했다.

아래 시간에는 입력 준비와 실제 AI 요청, 로컬 도구 처리, 결과 검증이 포함된다. 서버 시작 시 데이터 로딩 약 1초, HTTP·브라우저 렌더링·대표 FFT 추가 HTTP 조회·캐시 파일 저장은 제외했다. 마지막 검증 강화 이후 저장한 6개 최종 응답을 현재 코드로 다시 검증해 모두 오류 목록이 비어 있음을 확인했다.

|---|---:|---:|---:|---:|---:|---|

중앙값은 설비 8 **15.416초**, 설비 9 **13.776초**로 목표인 20초 이내다. 6회 중 4회는 AI 요청 1회로 완료했고, 5회는 추가 도구를 사용하지 않았다. 설비 9의 추가 조회는 이미 전달한 대표 FFT #4를 다시 확인한 호출로, 완전히 제거되지 않은 중복 조회 사례다. 보정이 필요한 경우에는 20초를 넘을 수 있다.

이전 코드의 측정은 설비 8 25.551초(9회 요청, 성공), 설비 9 35.012초(8회 요청·보정 2회 후 실패), 재측정 31.494초(9회 요청·보정 1회 후 성공)였다. 이전 측정의 표본 수가 적고 실제 응답·조회 계획·제공자 캐시 상태가 달라 동일 조건의 통계적 성능 비교로 일반화하지 않는다.

첫 요청의 입력 토큰은 설비 8 42,388, 설비 9 14,709였다. 전체 FFT를 모드·단위·측정점·RPM·대역·분해능별로 나누고, 월별 성분의 관측 극값과 대표 기록·관련 이력을 전달했다. 원본 FFT 배열은 전송하지 않았다. 전체 이력에서 수치 근거를 보존했지만 설비 8의 초기 입력은 여전히 크며, 향후 압축을 더 개선할 여지가 있다.

## 구현·회귀 검증

- 충분한 초기 근거에서 AI 요청 1회·도구 0회 완료.
- 추가 조회 2단계·4개 호출 제한과 보정 중 추가 조회 금지.
- 초기·추가 근거의 수치·기간·대표 기록 검증 및 모드/측정 조건별 압축.
- 중간 관측 극값·최초 이상 기록 보존과 해석불가 기록 제한 명시.
- 실제 측정 대역인 `500 Hz 조건` 허용, 근거 없는 500Hz 피크와 잘못된 500Hz 분해능 거부.
- 원인명에 직접 연결된 점검 요청 허용, 다른 대상의 점검 문구로 근거 없는 원인 주장을 면제하지 않음.
- 한국어 요약 예시는 가상 수치와 대응 진단 근거를 함께 제공하며, 1X 우세만으로 축정렬 불량을 주장하지 않도록 함.
- 기존 응답 API·캐시 TTL·강제 재분석·동시 요청 공유 유지, 분석 버전 변경으로 이전 결과와 분리.

앱 실행 후 `/dashboard?dataset=9`의 HTTP 200을 확인했다. 화면 배치를 변경하지 않아 브라우저 자동화와 모바일 검증은 생략했다.
